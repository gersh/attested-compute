# CH25 psi finite verifier

`sparkinterval-tg-psi-residual-shard` is a source-scale, bounded-memory CPU
implementation of the finite computation behind the `ch25-psi-1e13` atom. It
does not assert that a bounded run proves the atom, and its receipts explicitly
report `execution_attested = false` and `lean_atom_discharged = false`.

## Exact computation

The literal work domain is the half-open interval
`[2, 10_000_000_000_001)`. A runner invocation uses inclusive `--lower` and
`--upper` endpoints. It merges two independently generated ordered streams:

1. every prime in the shard, generated by the pinned primesieve source; and
2. every `p^k` in the shard with prime `p` and `k >= 2`. Completeness here is
   finite: `p <= floor(sqrt(upper))`, and checked integer multiplication stops
   at the first power above `upper`.

Each event adds an interval for `log(p)` to a Q64 state. The input prime is
below `2^53` and is therefore represented exactly as binary64. The pinned
CRlibm `log_rd` and `log_ru` endpoints are converted to Q64 by decoding the
binary64 sign, exponent, and significand; no floating-point scaling or cast is
used. CRlibm is built with contraction and unsafe reassociation disabled, and
its complete 21-test upstream suite runs as part of a fresh build.

Verify mode checks, with exact integers, the same endpoint reductions used in
`tg_verifier/finite_campaigns.py`. Before a jump at `v`, with lower state `L`,
it checks

```text
(v * 2^64 - L)^2 <= 2 * v * 2^128
```

when the difference is positive. After the jump, with upper state `U`, it
checks

```text
(U - v * 2^64)^2 * 25_000_000^2
  <= 19_764_819^2 * v * 2^128
```

when that difference is positive. At the closed source endpoint, the first
comparison is strict. Cheap integer filters decide ordinary rows; the runner
uses Boost.Multiprecision for every unresolved boundary case and reports the
fallback counts.

## Two-pass campaign shape

Summary mode returns the exact additive transition
`[delta_lower, delta_upper]` without accepting an incoming state. After all
fixed shards finish, an exclusive scan from the only root state `[0, 0]`
derives every shard input. Verify mode independently regenerates the shard
with that input and reports a singleton affine guard. This is directly
compatible with `tg_verifier/affine_guard_certificate.py`; the fixed plan and
ordered leaves prevent omission, duplication, or reordering.

Two SHA-256 commitments are retained:

- `event_sha256` commits just `(value, prime, exponent)`, allowing a human or
  independent prime-power implementation to compare structural coverage;
- `row_sha256` additionally commits both directed Q64 logarithm endpoints.

Summary and verify receipts must have identical deltas and commitments. A
single unsharded source run also checks the pinned total of 346,065,767,406
prime-power events.

## Lean receipt wire

`SparkInterval/TernaryGoldbach/PsiShardReceiptWire.lean` now parses the
newline-terminated compact JSON emitted directly by the C++ worker.  It is not
a parser for a second, manually transcribed descriptor.  The total checker
rejects:

- malformed UTF-8/JSON, whitespace-expanded or non-newline-terminated
  records, duplicate compact field spellings, unknown or missing fields;
- changed algorithm, atom, primesieve, CRlibm, encoding, or false
  trust-boundary flags;
- malformed SHA-256 text, inconsistent event counts, reversed or overflowing
  Q64 states, impossible fallback counts, or invalid ranges;
- summary records carrying prefix states or guards;
- verify records whose singleton guard, incoming state, outgoing state, and
  additive transition do not agree; and
- summary/verify pairs whose independently generated event digest, row
  digest, counts, or Q64 delta differ.

The list checker fixes the production 100,000-shard geometry, the zero root,
the 384 KiB sieve setting, gap-free shard adjacency, all derived incoming
states, the terminal endpoint, and the published total of 346,065,767,406
events.  Its soundness theorem returns only `ValidatedSourceWire`: a precise
finite statement about the receipt bytes and their opaque commitments.

The bounded fixture in
`SparkInterval/Tests/PsiShardReceiptWireTest.lean` is byte-for-byte C++ output
over `[2,100]`; the same structural digest, row digest, counts, and transition
are exercised by `tests/tg_psi_residual_shard_known_answers.py`.  Mutation
tests cover a mismatched replay digest, a claimed attestation, duplicate
fields, suffixes, and the stale summary-state shape described below.

This closes the receipt-format wire, not the source theorem.  The worker
currently retains only SHA-256 commitments to its event/log rows.  A Lean
checker therefore still cannot inspect the 346 billion rows, establish the
pinned CRlibm endpoints as bounds on `Real.log`, prove the committed
prime-power roster complete and ordered, or construct
`PsiPrimePowerCertificate.GapSourceScaleEvidence`.  In particular the
synthetic initial `[1,2)` constant-state gap must be represented explicitly
in that future row artifact.  Execution/attestation refinement is separate.

## Production campaign supervisor

`tools/tg_psi_residual_campaign.py` turns the shard runner into a resumable,
fail-closed campaign.  The default full-source plan contains exactly 100,000
ordered half-open shards of width 100,000,000 (the final shard is shortened by
one integer because the domain starts at 2).  Initialization captures the
runner binary, its C++ source, and the complete upstream manifest.  The plan
identity binds all three SHA-256 digests, the sieve configuration, every shard
range, and their order.

```bash
python3 tools/tg_psi_residual_campaign.py init \
  --runner build/psi/sparkinterval-tg-psi-residual-shard \
  --runner-source reference/tg_psi_residual_shard.cpp \
  --upstream-manifest specifications/PSI_UPSTREAMS.json \
  --output-dir /certificate-volume/ch25-psi

python3 tools/tg_psi_residual_campaign.py run \
  /certificate-volume/ch25-psi summary --workers 64
python3 tools/tg_psi_residual_campaign.py reduce \
  /certificate-volume/ch25-psi
python3 tools/tg_psi_residual_campaign.py run \
  /certificate-volume/ch25-psi verify --workers 64
python3 tools/tg_psi_residual_campaign.py finalize \
  /certificate-volume/ch25-psi
python3 tools/tg_psi_residual_campaign.py verify \
  /certificate-volume/ch25-psi
```

For a distributed run, `command OUTPUT summary INDEX` or `command OUTPUT
verify INDEX` prints the exact captured-runner argument vector for a worker.
Store its stdout as a receipt, then use `ingest OUTPUT PHASE INDEX RECEIPT`.
Concurrent ingestion is serialized around validation and immutable retention.
For a Slurm array, avoid one launch per leaf by using deterministic worker
groups:

```bash
python3 tools/tg_psi_residual_campaign.py run \
  /certificate-volume/ch25-psi summary \
  --worker-group-index "$SLURM_ARRAY_TASK_ID" \
  --worker-group-count 320 --workers 40
```

Group `g` receives exactly the leaf indices `g, g+320, g+640, ...`; all 320
groups are disjoint and cover the fixed plan. Grouping changes scheduler
granularity only: the campaign still retains one receipt per each of the
100,000 leaves in each pass.
Verification commands cannot be produced until every summary is present and
`reduce` has derived the exclusive scan from `[0,0]`.  `finalize` rejects an
incomplete phase, mismatched event/delta/row commitments, a substituted input
or guard, and any omitted, duplicated, or reordered leaf before emitting the
affine/Merkle certificate.

Short runs require the conspicuous `--bounded-test-upper-exclusive` option at
initialization and remain labeled `bounded_test`; neither their result nor a
full external certificate claims hardware attestation or a discharged Lean
atom.  The focused protocol suite is:

```bash
python3 -m unittest tests.test_tg_psi_residual_campaign -v
```

## Pinned build

The manifest `specifications/PSI_UPSTREAMS.json` binds every tracked byte of
primesieve and CRlibm in addition to their Git commits. Configure with clean
checkouts:

```bash
cmake -S . -B build/psi -DCMAKE_BUILD_TYPE=Release \
  -DSPARKINTERVAL_PSI_PRIMESIEVE_ROOT=/path/to/primesieve \
  -DSPARKINTERVAL_PSI_CRLIBM_ROOT=/path/to/crlibm
cmake --build build/psi --target sparkinterval-tg-psi-residual-shard -j
ctest --test-dir build/psi -R tg_psi_residual_shard_known_answers \
  --output-on-failure
```

The known-answer test compares bounded structural commitments and event counts
byte-for-byte with the exact Python implementation. It also checks that the
wider CRlibm interval encloses the Python rational-series interval and that
split-shard transitions compose to the unsharded transition.

Always compile the worker source before running this test.  During the wire
audit an older local build product was found which emitted `[0,0]` summary
states, while the current source and supervisor require both summary states
to be `null`.  The fresh current-source build emits `null`, and the Lean
fixture rejects the stale shape.  A pre-existing executable is not evidence
that the source consumer was compiled.

## Measured performance and remaining risk

On 2026-07-21, a strict-flags build on the 20-core ARM CPU of the local DGX
Spark processed 66,816,322 source-height events in each pass. Twenty concurrent
100,000,000-integer shards took 2.115 seconds for summary and 2.875 seconds for
verify, or 26.78 million event-passes/second in aggregate. Linear extrapolation
of both passes over the published source event count is 7.18 hours on that
host. This is an extrapolation, not a completed source run. Reproduce it and
retain the exact JSON report with:

```bash
python3 tools/benchmark_tg_psi_residual_shard.py \
  --runner build/psi/sparkinterval-tg-psi-residual-shard \
  --workers 20 --shards 20 --shard-span 100000000 \
  --output build/psi/tg-psi-source-height-benchmark.json --pretty
```

The 2026-07-25 wire audit repeated the same bounded geometry after rebuilding
the current source: 2.107 seconds for summary, 2.905 seconds for verify, 26.663
million event-passes/second, and a 7.21-hour linear projection.  A bounded
64/128/256/384/512/1024 KiB primesieve-cache sweep found no stable material
improvement; interleaved 384/512 KiB runs differed by roughly one percent or
less.  Keep 384 KiB as the reviewed production identity and calibrate it again
on the exact Azure CPU rather than changing a source pin from this noise.

This workload is CPU-oriented; the H100s are useful for other residuals but do
not accelerate the branch-heavy prime stream or CRlibm calls in this adapter.
An Azure campaign should launch many fixed CPU shards per node and distribute
them over all confidential-compute nodes. Before budgeting from the local
number, run a 1--2 billion event pilot on the exact Azure image: AMD SMT,
per-core CRlibm speed, sustained clocks, checkpoint overhead, and enclave I/O
can all reduce scaling. A closed 644-job Azure SEV-SNP materializer,
retained-export handoff, and signed-receipt path are now implemented as
described in `CH25_PSI_AZURE_MEASURED_DAG.md`; they have not yet been exercised
in a real source-height Azure run. The ordinary-Lean bridge is now explicit
in `PsiPrimePowerCertificate.lean`: its prime-power fold is proved equal to
Mathlib's `p.log n` expansion and directed prime-log bounds imply an enclosure
of `Chebyshev.psi`. The remaining physical refinement must show that the
retained CRlibm rows and complete two-pass commitments construct exactly its
`GapSourceScaleEvidence` (including exact prime-power gap coverage and state
constancy); the runner alone is finite-computation evidence, not a theorem.
For that reason the portfolio's psi semantic row remains disabled even though
its operational phase route is materializable.
