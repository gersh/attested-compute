# H100 implementation status

## What works without an H100

Run:

```sh
tools/build_h100_offline.sh
tests/test_h100_offline.sh
tools/build_h100_interval_batch_offline.sh
tests/test_h100_interval_batch_offline.sh
```

The build uses the installed CUDA toolchain to produce, under
`build/h100-offline`:

- PTX targeting `compute_90`.
- A Hopper cubin targeting `sm_90`.
- Static SASS and ELF metadata extracted from that cubin, plus a machine-
  readable conservative instruction audit.
- Toolchain metadata, a JSON build manifest, and SHA-256 checksums.

The manifest has `evidence_class: "offline_device_build"` and explicitly says
that no H100 execution, returned result, or production attestation occurred.
This is useful device-code evidence, but it cannot discharge an execution axiom
in Lean.

The second build performs the same kind of offline validation for the
primitive add/subtract/multiply/divide batch under
`build/h100-interval-batch-offline`. It compiles real `compute_90` PTX and an
`sm_90` cubin, requires exactly the eight directed binary64 PTX operations,
audits SASS, hashes sources/artifacts, and syntax-checks the strict H100 runner
wrapper. Only this primitive batch has an H100 offline path; the postfix
expression and generated-PTX paths remain DGX Spark-only.

Its manifest is deliberately explicit:

- `h100_presence_queried: false`;
- `h100_execution_attempted: false`;
- `host_executable_built: false`;
- `execution.result: null`; and
- `production_attestation.present: false`.

## Host architecture boundary

The DGX Spark build host is `aarch64`; most deployed H100 systems are hosted by
`x86_64` CPUs. PTX and cubin files are NVIDIA device artifacts and can be built
offline on the Spark. The portable CUDA Driver API source
`gpu/platform/h100/h100_probe_runner.cpp` is syntax-checked here, but a host
executable is a CPU artifact and must be built and run on the actual H100 host.
This path does not pretend that an `aarch64` syntax check validates an `x86_64`
binary or execution.

On the actual H100 host, compile and run the diagnostic runner against that
system's CUDA Driver library, for example:

```sh
c++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror \
  -I/usr/local/cuda/include \
  gpu/platform/h100/h100_probe_runner.cpp -lcuda \
  -o h100-probe-runner
./h100-probe-runner \
  --cubin build/h100-offline/h100_rounding_probe.sm_90.cubin
```

Its JSON is still `local_unattested`; a measured production workload must wrap
the algorithm/result statement in genuine, verified CC evidence.

## Mock integration path

After the offline build:

```sh
tools/run_h100_mock.sh --nonce a-development-nonce
```

The output is visibly `evidence_class: "mock_attested"`, unsigned, not production
acceptable, and says the algorithm was not executed. It exists only to develop
the manifest/certificate parser and exercise rejection at the existing Lean
import boundary.

## Production confidential-computing path

`tools/run_h100_cc_acceptance.sh` is deliberately fail-closed. It writes an
acceptance checklist, emits no evidence, and exits 78. It cannot be enabled with
a command-line flag.

The Lean axiom and structural checker already exist, but the trusted importer
that cryptographically verifies positive NVIDIA evidence and constructs the
private `H100HardwareEvidence` token does not. Consequently no current bundle
can produce an accepted production premise.

Completing production acceptance requires work on a real H100 CC system:

1. Build and test the CPU host runner for that system's architecture.
2. Enforce the intended H100 model, driver/toolkit policy, and confidential-
   computing mode before launch.
3. Supply a fresh verifier nonce and collect genuine NVIDIA hardware evidence.
4. Verify the evidence and certificate chain against pinned production trust
   roots, then bind it to the exact executable/device-image measurement.
5. Bind canonical input and parameter hashes, result hash, and successful
   completion to the attested run claim.
6. Test valid runs and negative cases (tampering, replay, stale evidence,
   measurement drift, non-CC/debug modes, and failure before completion).

Only evidence that passes those checks should reach the narrow Lean execution
axiom. Offline build manifests and mock evidence must always be rejected there.
