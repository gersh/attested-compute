# H100 offline work and production boundary

SparkInterval can prepare and audit H100 device artifacts without access to an
H100. The offline workflows cannot produce an H100 execution result, and the
repository cannot currently produce accepted confidential-computing evidence.

## Offline prerequisites

The scripts require Python 3, a C++20 compiler, `sha256sum`, and CUDA tools that
support `compute_90` and `sm_90`: `nvcc`, `nvdisasm`, and `cuobjdump`. They
default to `/usr/local/cuda`; `CUDA_ROOT`, `NVCC`, `NVDISASM`, `CUOBJDUMP`, and
`CXX` can select another installed toolchain.

Run the relative commands below from the repository root.

## Build or test

To create inspectable artifacts only:

```bash
./tools/build_h100_offline.sh
./tools/build_h100_interval_batch_offline.sh
```

Outputs are written under `build/h100-offline` and
`build/h100-interval-batch-offline`. They include `compute_90` PTX, `sm_90`
cubin/SASS and ELF metadata, instruction audits, toolchain records, manifests,
and SHA-256 files.

For self-testing builds instead, run:

```bash
./tests/test_h100_offline.sh
./tests/test_h100_interval_batch_offline.sh
```

Each test script invokes its corresponding build script in a separate test
directory and checks the generated artifacts and fail-closed behavior. Running
the artifact-only commands first is unnecessary unless both output sets are
wanted.

The diagnostic probe exercises all eight directed binary64 operations. The
interval-batch artifact contains the primitive add/subtract/multiply/divide
backend. The postfix expression and generated-polynomial execution paths do
not currently have H100 workflows.

The offline workflows do not query H100 presence, attempt execution, build a
host executable, return an arithmetic result, or produce a production
attestation. Their manifests record the applicable nonexecution fields.

## Host architecture boundary

PTX and cubin are device artifacts and can be built on DGX Spark's `aarch64`
host. A deployed H100 normally has an `x86_64` host, so the offline scripts only
syntax-check portable host-runner source. They do not claim to validate an
H100-host executable.

On an actual H100 host, the diagnostic runner can be compiled against that
system's CUDA Driver library, for example:

```bash
c++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror \
  -I/usr/local/cuda/include \
  gpu/platform/h100/h100_probe_runner.cpp -lcuda \
  -o build/h100-probe-runner
./build/h100-probe-runner \
  --cubin build/h100-offline/h100_rounding_probe.sm_90.cubin
```

That diagnostic remains a local, unattested run. It is not production
confidential-computing acceptance.

## Mock and production paths

`tools/run_h100_mock.sh` is a protocol fixture. Its output explicitly says no
algorithm ran and is always rejected by production policy.

`tools/run_h100_cc_acceptance.sh` is a fail-closed placeholder. It writes a
checklist, emits no evidence, and exits 78. There is no success flag.

Production acceptance requires a real supported H100 confidential-computing
system, a measured workload, fresh verifier nonce, pinned TCB and measurement
policy, cryptographic verification of NVIDIA evidence, binding to the exact
artifacts/input/result/completion statement, and replay/tamper tests. A future
trusted importer would validate that verifier's canonical output and construct
the private positive-evidence capability consumed by the explicit Lean
execution axiom. No such importer exists today.

See [Trust model](TRUST_MODEL.md) and [Run-bundle format](FORMAT.md) before
designing that integration.
