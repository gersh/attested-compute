# H100 native validation, offline artifacts, and trust boundary

SparkInterval has working H100-native probe, primitive interval, postfix
expression, real-integer zeta, and Lean-generated polynomial conformance
surfaces. It can also build inspectable H100 device artifacts without an H100.

These are local execution and conformance workflows. They do not enable
NVIDIA confidential-computing mode, collect an attestation report, verify an
NVIDIA evidence chain, or construct trusted Lean execution evidence. A
successful real-zeta run is a `local_unattested` bundle with
`hardware_evidence: false`.

## Requirements

Run all relative commands from the repository root.

The native CMake build requires:

- CMake 3.28 or newer;
- Python 3, a C++20 compiler, and Boost.Multiprecision headers
  (`libboost-dev` on Ubuntu);
- CUDA 11.8 or newer with `sm_90` support;
- `nvcc` and `cuobjdump`; and
- one build job unless memory use has been measured safely.

The full native validation additionally requires exactly one visible NVIDIA
H100 whose device name contains `H100` and whose compute capability is 9.0.
The strict runners reject `--allow-other-device`. The retained `h100_sm90`
real-zeta profile also requires an `x86_64` host and device index zero.

The generated-polynomial conformance path additionally needs `ptxas` and
`nvdisasm` on `PATH`. The artifact-only scripts use `sha256sum` and honor
`CUDA_ROOT`, `NVCC`, `NVDISASM`, `CUOBJDUMP`, and `CXX` where documented by
those scripts.

## Build and check the native CLIs without an H100

The native targets can be built for the current host without executing a CUDA
kernel. The CTest checks help and fail-closed argument handling, then uses
`cuobjdump` to require an `sm_90` device image in every relevant artifact:

```bash
cmake -S . -B build/h100-native \
  -DSPARKINTERVAL_BUILD_H100_NATIVE=ON \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/h100-native \
  --target sparkinterval-h100-native \
  --parallel 1
ctest --test-dir build/h100-native \
  -R '^h100_native_cli_offline$' \
  --output-on-failure
```

This produces:

```text
build/h100-native/sparkinterval-h100-probe-runner
build/h100-native/sparkinterval-h100-interval-batch
build/h100-native/sparkinterval-h100-expression-batch
build/h100-native/sparkinterval-h100-tg-r2star-factor-support
build/h100-native/sparkinterval-h100-tg-r2star-chunk
build/h100-native/sparkinterval-h100-tg-mobius-segment
build/h100-native/h100/h100_rounding_probe.sm_90.cubin
```

The explicit probe cubin path comes from the CMake target definition. The
primitive, expression, and three ternary-Goldbach executables contain embedded
`sm_90` images. Passing the offline CTest proves the build and pre-CUDA policy
wiring; it does not prove that any H100 executed the code.

The Möbius runner also implements the exact directed fixed-point checks for
both finite little-Mertens atoms.  On the H100 host it can be driven through
either complete endpoint, with atomic resume, by
[`tools/tg_mobius_campaign.py`](../tools/tg_mobius_campaign.py); see the
[little-Mertens campaign guide](algorithms/LITTLE_MERTENS_CUDA_CAMPAIGN.md).

For a Slurm cluster, the
[ternary-Goldbach H100 deployment guide](algorithms/H100_TG_CLUSTER.md)
builds a content-bound thirteen-job portfolio. Five jobs use these strict
`sm_90` runners; the remaining eight are explicitly classified CPU/FLINT or
exact-CPU sidecars rather than mislabeled GPU computations.

## H100 native local validation

On the physical H100 host, the supported all-in-one command configures and
builds the targets, runs the offline CTest, audits PTX/SASS, executes the
directed-rounding probe, and compares primitive and expression results with
the exact host oracle. It builds and offline-checks the three ternary-Goldbach
executables, but does not execute their kernels:

```bash
H100_BUILD_JOBS=1 ./tools/run_h100_native_validation.sh
```

Defaults are 10,000 random rows per primitive operation, 10,000 randomized
expression/row cases over eight programs, device zero, build directory
`build/h100-native`, and retained output directory
`build/h100-native-validation`. An explicit reproducible invocation is:

```bash
H100_BUILD_JOBS=1 ./tools/run_h100_native_validation.sh \
  --build-dir build/h100-native \
  --output-dir build/h100-native-validation \
  --primitive-count 10000 \
  --expression-count 10000 \
  --expression-program-count 8 \
  --device 0
```

The retained directory contains the probe result, static audit inputs and
reports, and primitive/expression conformance reports. Preserve it as local
diagnostic evidence only. The final message and probe record identify the
assurance as `local_unattested`; no confidential-computing evidence is
collected.

Use fresh `--build-dir` and `--output-dir` values for a retained verification
run. The complete fresh-directory recipe is in the
[reproducibility runbook](REPRODUCIBILITY.md#h100-native-local-validation).

## H100 real-integer zeta POC

After the native expression runner has been built, create a new work
directory. The zeta tool refuses to overwrite an existing destination:

```bash
mkdir -p build/examples
H100_ZETA_PARENT="$(mktemp -d build/examples/h100-zeta2.XXXXXX)"
H100_ZETA_DIR="${H100_ZETA_PARENT}/run"
python3 tools/run_zeta_poc.py run \
  --target-profile h100_sm90 \
  --work-dir "${H100_ZETA_DIR}" \
  --s 2 \
  --terms 4096 \
  --device 0
python3 tools/run_zeta_poc.py verify "${H100_ZETA_DIR}"
```

`--target-profile h100_sm90` selects the default executable
`build/h100-native/sparkinterval-h100-expression-batch`, the `sm_90` PTX
audit, the `h100_sm90` target profile, and the H100-specific versioned
algorithm definition. If the native runner was built elsewhere, add:

```text
--executable /absolute/path/to/sparkinterval-h100-expression-batch
```

The tool runs the exact input twice, requires byte-identical outputs, checks
the reported H100/9.0 identity, independently recomputes every `1 / n^s` row,
reruns the artifact audits, and packages the result as a canonical
`local_unattested` run bundle. It computes a positive real value at an integer
`2 <= s <= 64`; it does not locate or count zeros, verify the Riemann
hypothesis to a height, or provide confidential-computing attestation. See the
[real-zeta algorithm guide](algorithms/REAL_ZETA_POC.md).

## Lean-generated polynomial `sm_90` conformance

The proved typed polynomial generator now requires an explicit output target.
On an H100, its conformance harness can generate PTX for `sm_90`, audit it,
assemble it with `ptxas`, audit the cubin SASS, execute the exact cubin with the
strict H100 driver policy, and compare results with the exact reference
evaluator.

After the native CMake configuration exists, build the generator and driver,
then use a dedicated work directory:

```bash
./tools/safe_lake_build.py --target sparkinterval-gen
cmake --build build/h100-native \
  --target sparkinterval-generated-driver \
  --parallel 1
mkdir -p build/examples
GENERATED_H100_DIR="$(mktemp -d build/examples/generated-sm90.XXXXXX)"
python3 tools/run_generated_ptx_conformance.py \
  --generator .lake/build/bin/sparkinterval-gen \
  --driver build/h100-native/sparkinterval-generated-driver \
  --target sm_90 \
  --count 4096 \
  --work-dir "${GENERATED_H100_DIR}" \
  > "${GENERATED_H100_DIR}/summary.json"
```

The primary generated files include:

```text
${GENERATED_H100_DIR}/kernel.ptx
${GENERATED_H100_DIR}/kernel.sm_90.cubin
${GENERATED_H100_DIR}/kernel.sm_90.sass.txt
${GENERATED_H100_DIR}/signed-zero-kernel.sm_90.cubin
${GENERATED_H100_DIR}/report.json
```

This is the generated polynomial path, not the division-capable zeta path.
The H100 driver requires the explicit `--target sm_90` binding and disables
the cross-device override. The current closure and canonical generated-cubin
packager are DGX/`sm_121` specific, so do not run them over this H100 work
directory. Treat the generated report as local conformance evidence, not as a
CC-attested run bundle.

## Artifact-only offline workflows

No H100 is needed for the older standalone device-artifact builders:

```bash
./tools/build_h100_offline.sh
./tools/build_h100_interval_batch_offline.sh
```

Outputs are written under `build/h100-offline` and
`build/h100-interval-batch-offline`. They include `compute_90` PTX, `sm_90`
cubin/SASS and ELF metadata, audits, toolchain records, manifests, and SHA-256
files. To build and self-test into isolated test directories instead, run:

```bash
./tests/test_h100_offline.sh
./tests/test_h100_interval_batch_offline.sh
```

Each test script invokes its corresponding builder. Running both the
artifact-only and self-testing commands is unnecessary unless both output sets
are wanted. These workflows do not query H100 presence, execute a kernel,
return an H100 arithmetic result, or produce attestation.

## Confidential-computing and Lean boundary

`tools/run_h100_mock.sh` is a protocol fixture. Its output explicitly says no
algorithm ran and production policy rejects it.

`tools/run_h100_cc_acceptance.sh` is a fail-closed placeholder. It writes a
checklist, emits no positive evidence, and exits 78. There is no success flag.

Production Azure NCC acceptance uses a separate implemented path: an exact
`Standard_NCC40ads_H100_v5` deployment, measured workload, fresh off-VM
challenge, pinned TCB and measurement policy, independent Azure/vTPM and
NVIDIA evidence appraisal, an HSM-signed receipt, and a reviewed source-pinned
Lean registry entry. See the
[Azure confidential-compute guide](AZURE_CONFIDENTIAL_COMPUTE.md). The legacy
stub above remains negative-test infrastructure and is not that path.

Only the source-admitted receipt route can reach the sole Lean execution axiom,
`accepted_run_certificate_sound`. It then yields the exact historical outcome
and fixed formal `Runs` semantics for a matching closed registered invocation.
The legacy `checkH100Attestation` structure remains a diagnostic, and
`RunCertificate.check` rejects its `.h100Hardware` constructor even when that
diagnostic succeeds. It therefore cannot establish `AlgorithmReturned`,
`ProducedOutcome`, or `Runs`. The tracked receipt registry is empty: no
production H100 receipt or registered zeta invocation exists today.

Attestation does not prove that arbitrary user-space code caused the output;
production policy must cover an immutable measured runner and executable
closure. It also does not prove the algorithm's mathematics, which requires a
closed invocation and an ordinary Lean soundness theorem.

PTX and SASS audits, exact differential replay, device-name checks, and hashes
are valuable but do not formally prove `ptxas`, the CUDA driver, the host, or
physical H100 semantics. See the [trust model](TRUST_MODEL.md) and
[run-bundle format](FORMAT.md) before interpreting or integrating the output.
